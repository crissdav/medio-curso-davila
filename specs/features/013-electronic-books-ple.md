# SPEC-013: Electronic books (PLE) — formats 14.1 and 12.1

- **Status:** Draft
- **Date:** 2026-11-04
- **Related:** UC-29, UC-30, UC-31 · SPEC-001, 002, 009, 010 · RS 234-2006/SUNAT, RS 286-2009/SUNAT · [Traceability matrix §11–12](../../docs/05-traceability-matrix.md) · [ledger.schema.json](../schemas/ledger.schema.json)

## Summary
Generate from the domain the two formal records that SUNAT requires from ABC: **format 14.1** (sales
and income record, code 140100) and **format 12.1** (permanent inventory in physical units, code 120100).

## Motivation
RS 234-2006/SUNAT requires formal books and records, and a report in Excel is not one of them. Every sale and
every warehouse movement already has the data; these formats only need it modelled and traced.

## Design
- `GenerateSalesRecordUseCase` and `GenerateInventoryRecordUseCase` produce `SalesRecordLine` and `InventoryRecordLine` rows in the domain.
- `PleExporterPort` turns them into the TXT file. **SIRE (RVIE)**, which replaces the PLE sales record for obligated taxpayers, is a second adapter of the same port (`SireExporterAdapter`); the use case does not change.
- Format 12.1 is not part of SIRE: it continues on the PLE.

## File rules
| ID | Rule |
|---|---|
| R-01 | Period: the API uses `YYYYMM`; the file uses `YYYYMM00` (field 1). A document or movement belongs to the period of its date. |
| R-02 | The CUO (field 2) is unique per operation: `{documentType}-{series}-{number}` for sales. The entry number (field 3) starts with `A` (opening), `M` (month) or `C` (closing). A sale uses the same CUO in both books. |
| R-03 | Dates are written `DD/MM/YYYY`; amounts have up to 2 decimals, without thousands separators. |
| R-04 | Document types follow table 10: catalog 01 codes 01, 03, 07 and 08 keep the same value. |
| R-05 | Customer data is optional for a sales receipt below S/ 700 issued to customer `-` (catalog 06). Catalog 06 converts to table 2 with the same code, except `A` → `0`. From S/ 700 the annex requires each sales receipt to be recorded in detail; lower ones may be consolidated per day with `finalNumber`. |
| R-06 | Amounts: field 14 **excludes ISC**, which goes in field 20; ICBPER goes in field 23. The sum of fields 13–24 must equal field 25. |
| R-07 | Credit and debit notes fill fields 28–31 with the modified document. Credit notes carry negative amounts: type 04 / 05 discounts go in fields 15 and 17; all other types go in the original columns (design decision to validate with the accountant). |
| R-08 | Field 26 uses the 3-letter currency code. Field 27 is `#.###`; PEN is exported as `1.000`. Field 33 is filled only when the rate differs from the published one. |
| R-09 | Field 34 is `1` only if the document was paid with a payment medium; otherwise it is empty. |
| R-10 | Status (14.1 field 35, 12.1 field 19): `1` belongs to the period; `8` earlier period not recorded; `9` earlier period already recorded. In 14.1, `2` marks a voided document (`VOIDED`, or `REJECTED` with its number unusable) with zero amounts, and `0` an optional entry with no IGV effect. |
| R-11 | Format 12.1 has one line per movement, with the establishment and existence type of the movement; the description is cut at 80 characters. |
| R-12 | Field 5 holds the own-catalog code and field 8 the UNSPSC catalog code (table 13). Field 9 is the 8-digit UNSPSC code plus `00000000`. A product without `sunatProductCode` or with `requiresReview = true` blocks generation with 422 `PRODUCT_REVIEW_PENDING`. |
| R-13 | For operation types 01–06 the document type cannot be `00`. A document without series or number is written `0`. |
| R-14 | Units are exported in **table 6, not UN/ECE**, through [unit-mapping-cat03-to-table06.json](../ple-tables/unit-mapping-cat03-to-table06.json), and the quantity is multiplied by its factor (e.g. `MLT` → `08` × 0.001). `ZZ` services create no movement. |
| R-15 | Entries are positive or `0.00`; **exits are negative or `0.00`**; both are mutually exclusive. The first record per product and establishment is the opening balance (table 12 code 16). `balanceAfter` is the balance of the printed format; it is not part of the TXT. |
| R-16 | File name: `LE` + RUC + `YYYYMM00` + book code (`140100` / `120100`) + `00` + operations indicator (`1` active, `2` not obliged, `0` closure) + content (`1` with data, `0` empty) + currency (`1` PEN, `2` USD) + `1` (generated by the PLE) + `.TXT`. |
| R-17 | Fields are separated by `\|` and every record ends with `\|`. The `&` character is not allowed in fields 2 and 3. |
| R-18 | A book is generated only for a **closed** period (`POST /ledgers/periods/{period}/closure`); otherwise 409 `PERIOD_NOT_CLOSED`. Closing requires no document in `SIGNED` or `PENDING_SUBMISSION` (422 `PERIOD_HAS_PENDING_DOCUMENTS`). Later changes to a closed period are recorded in a later period with status `8` or `9`. |
| R-19 | Movements migrated from the legacy system appear only in the books of their own historical periods (SPEC-009), and they produce no entry in format 14.1 because they are not tax documents. |

## Acceptance criteria
- **AC-1:** Given the closed period 202610 with the reference invoice, when I request `GET /ledgers/sales/202610`, then I get a record equal to [the 14.1 sample](../ref/ple/LE2012345678620261000140100001111.TXT).
- **AC-2:** Given the same period and an opening balance of 100 units of `CER-620`, when I request `GET /ledgers/inventory-units/202610`, then I get a record equal to [the 12.1 sample](../ref/ple/LE2012345678620261000120100001111.TXT), with exits `-12.00` and final balance 88.
- **AC-3:** Given an open period, when I request a book, then I get 409 `PERIOD_NOT_CLOSED`.
- **AC-4:** Given the period `202613`, when I request a book, then I get 400.
- **AC-5:** Given a beer sold in `NIU`, when I generate format 12.1, then the unit is `07`.
- **AC-6:** Given a credit note, when I generate format 14.1, then fields 28–31 hold the modified document and its amounts are negative.
- **AC-7:** Given a product with `requiresReview = true` with movements in the period, when I request format 12.1, then I get 422 `PRODUCT_REVIEW_PENDING`.
